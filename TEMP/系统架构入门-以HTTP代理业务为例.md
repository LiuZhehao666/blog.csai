# 系统架构入门：以 HTTP 代理业务为例

> 目标读者：刚接触代理/网络的同学。本文用“HTTP 代理公司常见业务形态”串起系统架构的核心要素：组件划分、数据流、关键指标与常见坑位。

先给小白一个总比喻（把“代理系统”想成一个大型机场/收费站）：
- 你从“入口匝道”进来（接入层），先过“安检/验票”（鉴权计费），再由“调度台”给你分配“起飞跑道/出口航线”（策略与出口池），全程还有“监控摄像头+黑匣子”（观测系统）记录发生了什么。

小白口诀：**入口接人 → 验票计费 → 调度派车 → 出口上路 → 全程监控**。

---

### 1. 先把“HTTP 代理”分成两类工作模式

- **显式代理（Explicit Proxy）**
  - 客户端明确配置代理（浏览器/代码里设置 `http_proxy`、`https_proxy`），请求先到代理，再到目标站。
  - HTTPS 常见走 **CONNECT 隧道**：客户端向代理发 `CONNECT host:443`，代理建立到目标的 TCP 连接后，后续 TLS 数据在这条隧道里透传。
- **透明/旁路/网关式（Transparent / Gateway / Sidecar）**
  - 客户端不显式配置代理（通过网关策略/iptables/服务网格等把流量导入）。
  - 这类更偏网络/基础设施能力，涉及更多路由与 ACL。

你们公司“做 HTTP 代理”，大概率核心在显式代理（以及 CONNECT 隧道）这一套；但很多系统设计思想在两类模式里通用。

---

### 2. 一条请求会经过哪些组件（最小可用架构）

以“客户使用你们的代理访问外网”为例，一个最小可用链路通常包含：

- 通俗类比（按“机场”来记）：
  - 接入层 = 机场入口闸机
  - 鉴权计费 = 安检/验票/计费闸机
  - 策略调度 = 塔台/调度中心
  - 出口池 = 多条跑道/多条航线（不同质量/成本/地域）
  - 观测系统 = 摄像头 + 黑匣子 + 仪表盘

- **接入层（Edge / Gateway / Proxy Frontend）**
  - 处理：监听端口、协议解析（HTTP/1.1、CONNECT）、基础限流、基础黑白名单、请求上下文（trace id）。
  - 形态：Nginx/Envoy/自研 Go/Rust 代理。
- **鉴权与计费（Auth/Billing）**
  - 处理：API Key/用户名密码/Token，套餐校验，计费粒度（按流量/按时长/按请求）。
  - 注意：鉴权通常必须低延迟，否则会拖垮吞吐。
- **策略与调度（Policy/Scheduler）**
  - 处理：选择出口（地域/运营商/质量/成本）、会话粘性、失败切换、并发配额。
  - 常见策略：Round-robin、权重、基于延迟/成功率的动态权重。
- **出口池（Egress Pool）**
  - 处理：维护可用出口 IP、健康检查、灰度、回收。
  - 关注：出口失败类型（连接失败/握手失败/目标封禁/超时）要分清。
- **观测系统（Observability）**
  - 指标：QPS、并发连接数、成功率、P50/P95 延迟、上行/下行字节、错误码分布。
  - 日志：访问日志、鉴权日志、调度选择、出入口异常原因。

### 3. 关键数据流：HTTP 与 CONNECT 的“差异点”

#### 3.1 普通 HTTP（非 CONNECT）

1) 客户端发 HTTP 请求到代理  
2) 代理校验鉴权/策略  
3) 代理向目标站发起 HTTP 请求并转发响应  

关键点：
- 代理需要正确处理 `Host`、绝对 URI/相对 URI、连接复用（keep-alive）、以及请求体转发。

通俗比喻：
- 普通 HTTP 像“代购/代下单”：你把清单给代理（请求），代理去目标店铺下单（访问目标），再把包裹带回来（响应）。代理需要看懂你写的清单格式（HTTP 语义）。

#### 3.2 HTTPS via CONNECT（更常见）

1) 客户端 → 代理：`CONNECT example.com:443 HTTP/1.1`  
2) 代理 → 客户端：`HTTP/1.1 200 Connection Established`  
3) 客户端与目标站的 TLS 握手数据在隧道里透传（代理只做 TCP 转发，默认看不到明文）  

关键点：
- 这时代理更像“TCP 隧道转发器”，核心是**稳定的双向拷贝**、**超时**、**半关闭处理**和**背压**。
- 如果业务要求“看明文/做内容审计”，就涉及 MITM（需要证书体系），架构复杂度会显著上升。

通俗比喻：
- CONNECT 更像“打通一根不透明的水管”：先把水管接好（建立隧道），后面水里装的是什么（TLS 明文）默认你是看不到的，你只负责别漏水、别堵、别超时。

参考：
- MDN CONNECT 方法（用于理解语义）：[MDN - CONNECT](https://developer.mozilla.org/en-US/docs/Web/HTTP/Methods/CONNECT)
- HTTP 语义 RFC（更权威）：[RFC 9110](https://www.rfc-editor.org/rfc/rfc9110)

### 4. 架构设计里最容易忽视的 10 个点

- **连接生命周期**：HTTP/1.1 keep-alive、CONNECT 的长连接，决定了你要按“连接数”而非“请求数”规划容量。
- **超时分层**：DNS 超时、TCP 建连超时、TLS 握手超时、首包超时、空闲超时，必须分开配置与统计。
- **错误归因**：同样是“访问失败”，可能是鉴权失败/出口不可用/目标拒绝/网络抖动/超时；归因不清会导致调度策略失效。
- **限流位置**：接入层限流 vs 鉴权后限流 vs 出口侧限流，效果完全不同。
- **会话粘性**：有些网站/业务需要同一用户固定出口 IP（否则风控/登录态会出问题）。
- **IP 质量评价**：成功率、封禁率、延迟、抖动、TLS 指纹兼容性等，都可能纳入评分。
- **资源隔离**：按租户/套餐隔离并发与带宽，避免“噪声用户”拖垮全局。
- **重试策略**：代理内部重试很危险，可能放大流量；通常只对“建连失败/早期失败”做有限重试，并记录重试链路。
- **观测与采样**：全量日志成本高，采样策略要与排障需求匹配。
- **安全**：滥用检测、黑名单、审计、密钥轮换、敏感配置加密。

### 5. 给新同学的“落地练习”

建议你用 2 个小时做出一个可解释的实验：

1) 用任意代理（或自写）访问一个 HTTPS 网站  
2) 抓包观察 CONNECT 建立与后续 TLS 数据透传  
3) 记录：代理日志里你能看到什么（域名、端口、字节数、时长），看不到什么（TLS 明文内容）  

如果你能把这套讲清楚，系统架构这块你就入门了：因为你已经知道“系统在做什么、看得见什么、哪里会出错、如何定位”。

---

### 6. 小结

HTTP 代理系统的架构核心不是“能转发”，而是：
- **可控**（鉴权、配额、策略）
- **可扩展**（出口池、调度）
- **可观测**（指标、日志、追踪）
- **可运营**（质量、成本、风控）

下一步如果你想把本文进一步贴合你们公司业务，最关键的补充信息是：你们主打的产品形态是 **动态提取**、**隧道长连**、还是 **静态独享**（或者三者都有）。
