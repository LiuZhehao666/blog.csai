# 提示词工程化：评测、回归、RAG、工具调用

上一节我们把提示词当成“需求说明书”来写。本节把它进一步工程化：让提示词**可评测、可回归、可追溯、可上线**。

## 1. 为什么要工程化（从“能用”到“稳定”）
很多提示词在你本机看起来很好，但一旦遇到不同输入、不同模型版本、不同温度参数，就开始“漂移”。工程化的核心目标是：
- **稳定性**：同类输入输出结构一致，质量波动可控
- **可回归**：改一行提示词不会悄悄把旧场景弄坏
- **可追溯**：尤其在 RAG 场景下，回答能追溯到来源证据
- **可运维**：可观测、可降级、可审计

## 2. 评测集（Eval Set）：用小样本抓住大问题
### 2.1 评测集该长什么样
建议从 20~50 条开始（小而精），每条包含：
- **输入**：真实用户问题/真实文档片段/真实日志（必要时脱敏）
- **期望输出**：结构要求 + 关键要点（不一定要全文逐字一致）
- **打分标准**：通过/不通过 或 0~2/0~5 分的分档规则
- **标签**：场景类型（摘要/抽取/问答/代码/翻译）、难度、风险等级

### 2.2 三类“必备用例”
- **边界用例**：输入很短/很长/信息不足/包含噪声/多语言混杂
- **反事实用例**：输入里没有某字段，期望输出必须为 `null/待确认`
- **格式用例**：强约束 JSON/表格输出，验证是否“格式漂移”

### 2.3 评测的常见指标（够用版）
不用一上来就追求复杂指标，先把“线上会痛”的问题压住：
- **格式正确率**：JSON 能否解析、字段是否齐全、是否多输出解释文本
- **事实一致性**：关键事实是否来自输入（尤其 RAG）
- **拒答/澄清率**：输入不足时能否先问问题，而不是瞎编
- **成本**：token 消耗（输入 + 输出），以及响应时延

## 3. 回归测试：改提示词也要像改代码一样
### 3.1 版本化你的提示词
把提示词当“配置/资产”管理：
- 给提示词加版本号：`prompt_v1`, `prompt_v2`
- 记录变更原因：解决了哪个线上问题、提升了哪个指标
- 固定关键参数：模型版本、temperature/top_p、输出长度上限

### 3.2 两种回归策略
- **静态回归**：同一批评测集，每次改动都全量跑一遍（最常用）
- **灰度回归**：线上小流量/内部用户先用新版本，对比旧版本指标再放量

### 3.3 “不允许退步”的红线
建议先定 3 条红线，任何一条变差就不合并：
- JSON 解析失败率不能上升
- 幻觉（编造不存在事实）不能上升
- 关键场景通过率不能下降（比如客服合规、财务数字）

## 4. RAG 工程化：回答必须“可引用、可追溯”
RAG（检索增强生成）并不等于“把一段文档塞进去让模型自由发挥”。工程化重点在两件事：**检索质量**和**引用约束**。

### 4.1 最小 RAG 流程（概念版）
1) **切分（chunk）**：把文档按段落/标题/长度切片  
2) **向量化（embedding）**：把 chunk 编码成向量  
3) **召回（retrieve）**：按相似度找相关 chunk  
4) **重排（rerank，可选）**：提升最相关证据排位  
5) **生成（generate）**：模型必须基于证据回答，并输出引用

### 4.2 让回答“带引用”的提示词模板
核心原则：**不允许无证据的断言**。

```markdown
你是严谨的知识库问答助手。
任务：基于【证据】回答【问题】。

硬性约束：
1) 只能使用【证据】中的信息回答；证据中没有的内容必须说“未在证据中找到”，不要猜测；
2) 每个关键结论都要在句末标注引用，如 [S1] / [S2]；
3) 输出包含两部分：回答 + 引用清单（列出每个引用对应的证据片段）。

【问题】
{question}

【证据】
[S1] {chunk_1}
[S2] {chunk_2}
[S3] {chunk_3}

【输出格式】
### 回答
...
### 引用清单
- [S1] ...
- [S2] ...
```

### 4.3 常见坑与修复
- **坑：证据太多太杂** → 修复：召回数量别贪（先 3~6 条），必要时加重排
- **坑：chunk 切太大** → 修复：按标题/段落切，控制每片长度，保留“来源信息”
- **坑：模型不引用** → 修复：把引用写成硬约束，并在输出格式里强制出现“引用清单”

## 5. 工具调用与结构化输出：让模型“会办事”
当任务需要“查数据/算数字/跑代码/访问接口”时，别让模型纯生成，应该让它**调用工具**。

### 5.1 工具调用的基本模式
- 模型先输出：要调用什么工具 + 参数（结构化）
- 系统执行工具：得到结果
- 把结果回填给模型：让它基于结果生成最终回答

### 5.2 结构化输出模板（JSON Schema 风格）
目标：减少格式漂移，便于后续程序处理。

```markdown
你是结构化输出助手。
任务：根据【输入】输出严格的 JSON。

硬性约束：
1) 只输出 JSON（不要代码块、不要解释、不要多余文本）；
2) 必须符合以下 schema；不存在的信息用 null；
3) 字段名必须完全一致，顺序不重要，但不得增加字段。

【输入】
{input}

【schema】
{
  "type": "object",
  "properties": {
    "intent": { "type": ["string","null"] },
    "entities": {
      "type": "array",
      "items": {
        "type": "object",
        "properties": {
          "name": { "type": "string" },
          "value": { "type": "string" }
        },
        "required": ["name","value"]
      }
    },
    "need_clarification": { "type": "boolean" },
    "clarifying_questions": { "type": "array", "items": { "type": "string" } }
  },
  "required": ["intent","entities","need_clarification","clarifying_questions"]
}
```

### 5.3 “先问再答”工程化（非常好用）
对真实业务来说，很多输入天然不完整。与其让模型瞎编，不如把“提问”变成流程的一部分：
- 输出 `need_clarification=true` 时，前端/机器人只展示澄清问题
- 用户补充后再二次调用生成最终结果

## 6. 最小落地清单（你可以照着做）
- **提示词资产化**：文件化 + 版本号 + 变更记录
- **评测集**：先 30 条，覆盖边界/反事实/格式三类
- **回归门槛**：3 条红线（格式、幻觉、关键场景通过率）
- **RAG 引用**：回答强制引用 + 引用清单 + 证据缺失就明确说缺失
- **工具优先**：计算/查询/校验交给工具，大模型负责规划与表达
